## Safe implementation sequence

1. **Workspace boundary design and migration contract.** Defined in [the workspace isolation design](TENANT_ISOLATION_DESIGN.md): server-resolved identity, resource ownership, migration/rollback, worker boundaries, adversarial acceptance cases, and a shared-mode go-live gate. Baseline evidence: `SQLiteStateStore` APIs are keyed by `case_id` and have no workspace argument (`rfq_assistant/persistence.py:19-73`); the case schema has `case_id` but no workspace owner (`rfq_assistant/schemas/models.py:178-205`); the authenticated RFQ list/read/source handlers fetch global manager state (`rfq_assistant/api/app.py:505-555`).
2. **Backend persistence isolation.** Add workspace-scoped compound keys/foreign keys and migration, then pass authenticated workspace context through every case, catalog, audit, quote, job, and export path. Avoid user-controlled workspace IDs. Test guessed IDs, cross-workspace list/read/edit/delete, and worker/job fencing.
3. **File/object isolation and frontend identity wiring.** Bind source/export objects and URLs to server-resolved workspace ownership; test direct object references and delete/retention behavior. Only then consider multiple workspaces in one deployment.
4. **Multi-attachment case model.** Implemented in PR #77. The additive source manifest preserves legacy single-source cases; bounded intake accepts pasted email plus several files; each source has a status and stable ID; lines, coverage and quote citations keep the originating source; duplicate and conflict cases require review; and a failed source can be retried without removing successful lines. Synthetic backend, quote-citation and Playwright checks cover the workflow. PR #78 migrates safe legacy named source files into the opaque hashed layout without changing case snapshots or logical source names. This PR adds a 26 MiB ASGI multipart request cap before Starlette parsing. A trusted reverse-proxy/server cap is still required to bound upstream buffering and service ingress.
5. **Security remediation in small PRs.** Review upload/parser/converter subprocess boundaries, ClamAV failure behavior, shared rate limiting, CSRF/CORS/security headers, output escaping, logging/secrets, and retention against current code and deployment assumptions. Fix only verified issues and record exploit-oriented tests.
6. **Measured reliability and performance.** Add synthetic 10/50/100/500-line plus varied-attachment runs; report intake, extraction/OCR/model, queue, matching, review, and export p50/p95, throughput, memory and failures. Add timeout, cancellation, duplicate submission, lock, worker kill/restart and idempotency cases. Optimize only measured bottlenecks.
7. **Quality gate and evaluation readiness.** Triage current advisory IDs; fix dependency compatibility in isolated PRs; ratchet mypy by module; verify OpenAPI generation. Publish the synthetic/adversarial scorecard, buyer-demo checklist, operator feedback form, and an opt-in path for consented/redacted customer examples. Keep all commercial claims unvalidated until measurements exist.

## Readiness decision

The repository supports a local synthetic demo, including a synthetic email-plus-attachments workflow. Per-user roles work within one isolated workspace. It is **not ready for a shared multi-organization deployment or production use**: tenant-scoped storage/API authorization, edge-enforced ingress limits, operational retention/recovery, and independent customer validation remain blockers. A controlled pilot also requires the onboarding, privacy, operational, and customer-approved evaluation gates in [PRODUCTION_CUSTOMER_ONBOARDING.md](PRODUCTION_CUSTOMER_ONBOARDING.md). No customer accuracy, capacity, or ROI result is claimed.
