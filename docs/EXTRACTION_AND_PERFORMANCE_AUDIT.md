# Extraction and performance audit

This document separates (1) patterns observed during the user-authorized, read-only review of `Bynd-ai/chat` `origin/prod-trunk` at commit `246c81f7` (the user's dirty local feature checkout was preserved and not treated as this ref), (2) RFQ Assistant's verified current implementation, and (3) proposed follow-up work. The reference repository is architectural guidance only; its source, datasets, secrets, customer data, and employer data are not part of this project.

## Reference patterns observed

The reference system separates interactive API requests from expensive document processing. Uploads are queued for durable workers, processing attempts are claimed with leases/heartbeats, and retries or dead-letter handling cover stuck work. Processing is idempotent at the document boundary. CPU-heavy work is bounded with process pools and concurrency limits.

For PDFs, the reference flow extracts native text first, classifies pages, and runs OCR only where needed. OCR work is split into bounded page batches, submitted and polled asynchronously with shared provider pacing and retry handling. It accounts for incomplete pages and keeps page-level text, geometry, and processing timing. Damaged pages can be handled independently so one bad page does not necessarily discard the rest.

For workbooks, the reference moves heavy reads into an isolated reader, opens workbooks once in read-only mode, caches bounded ranges, checks file versions, and limits per-workbook concurrency and memory. Its profiling approach measures deterministic synthetic workloads separately from end-to-end/provider workloads, including latency, memory, queue/health behavior, and stage counters.

These are useful design patterns, not proof that the same implementation or performance results will transfer to RFQ Assistant.

## RFQ Assistant today

The current local prototype accepts uploads through FastAPI, validates and stores the original, creates a processing case, and enqueues parsing/matching work in a SQLite-backed worker by default. The worker claims jobs with renewable leases, heartbeats, bounded retries, and a fenced case-snapshot commit: a stale worker cannot overwrite the newer lease owner's result. Startup reconciliation repairs the persist/enqueue crash window. This is a single-host local queue, not a multi-host production service. The PDF path keeps pypdf's row-shaped native text, uses PyMuPDF to triage sparse/image-heavy pages, and runs at most two bounded local Tesseract OCR jobs concurrently. If page triage fails, every page goes through the bounded OCR path; OCR failures are blocking and OCR-derived lines remain marked for source review. A comparison on a synthetic RFQ fixture showed that PyMuPDF's plain text extraction split table cells onto separate lines, so it was not used as the row parser. CSV and XLSX readers stream rows; XLSX is opened read-only with formula text preserved but never calculated, headerless sheets are conservatively inferred and flagged, and hidden sheets are surfaced for review. Legacy `.xls` is converted by a time-limited LibreOffice subprocess with a private temporary profile and an environment that excludes application credentials; the original stays available for human review. This is process isolation only, not an OS/container security sandbox, so production deployment must run conversion inside a restricted worker/container. We intentionally avoid the reference project's per-sheet LLM workbook summaries because its manual notes measured 39–52 seconds on 49–93 sheet books; RFQ line extraction instead uses deterministic rows and calls Luna only for unresolved/unstructured input. Matching remains deterministic exact part-number plus manufacturer matching against the imported catalog. SQLite stores case, line, audit, and ingestion-job state; originals remain in local storage.

The optional extraction adapter added in this branch is disabled by default. If explicitly enabled and configured for the exact `gpt-6-luna` model, it sends bounded source excerpts for unresolved lines, unclassified candidate regions, or (when deterministic parsing returns no rows) bounded source segments. It requests JSON, validates a strict schema, checks quoted evidence against the source, requires quantity evidence, and rejects a decimal quantity if conversion to the application's numeric representation would overflow or change its value. A failed extraction validation gets one bounded repair attempt; a second Luna call reviews accepted LLM proposals and can only flag conflicts/uncertainty. A malformed or unavailable review pass routes each affected row to individual human review. Neither model call can choose catalog records or approve lines. Candidate regions omitted by Luna remain visible as manual-review rows, and structured rows are preserved when the fallback fails. OCR-derived PDF page text and hidden workbook rows are carried to fallback with provenance warnings. Synthetic/offline tests exercise the validation contract; a separate live synthetic Luna request was made as described below; no customer RFQ data was sent.

The API records privacy-safe stage timings without logging document content. Each model call also logs the configured model ID, outcome, latency, and provider-reported input/output token counts (or `unknown` when absent); it never logs prompts, response bodies, keys, or customer identifiers. This supports cost/latency tuning but does not compute currency cost. These measurements are instrumentation, not a performance claim. Upload validation, byte transfer, and persistence still happen in the request; parsing, local OCR, matching, and any optional remote model call run in the worker. API clients must poll/read case state and handle terminal processing failures.

## Current gaps and risks

- OCR is local and optional. Install Tesseract and enable `RFQ_LOCAL_OCR_ENABLED` to process image-heavy pages; OCR covers at most 10 pages per document with per-page rendering/time bounds. Pages over that cap fail closed for manual handling.
- Legacy `.xls` conversion now has timeout, reduced subprocess environment, output-size/archive/macro checks, and synthetic contract tests; run it inside an OS-level sandbox before production. It still needs adversarial fixtures for malformed BIFF/OLE structures and macro-bearing inputs. Workbook row iteration is bounded, but additional adversarial fixtures should cover inflated worksheet dimensions, exotic header arrangements, formula-backed MPN/manufacturer cells, and sparse text with embedded page images.
- The SQLite queue is single-host only. It has bounded retries and lease recovery, but needs shared database/queue semantics, process supervision, worker health monitoring, and deployment/load testing before multi-host production use.
- Source-segment construction now fails closed at 500 excerpts, 40,000 total characters, or 20,000 rows per workbook sheet. Remaining non-empty PDF text lines, text/email lines, and CSV/XLSX rows that do not map to structured fields are retained as fallback candidates (up to 500 unresolved regions); explicit document/email metadata and blank regions are filtered. If Luna is disabled, fails, or omits a candidate, that content becomes an individual review row. A compact content-free coverage manifest is persisted and shown in the workbench, including on parser failures. It groups counts and a hash by PDF page, workbook sheet/table, or text document; records empty pages/sheets, OCR decision/outcome, detected header row, hidden-sheet status, formula-backed field count, and explicit parser-limit/failure state. This is a source-processing receipt, not row-level provenance; line locators remain the evidence path for each extracted or review item.
- The reviewer worklist is implemented: all exceptions are listed separately, up to five clean rows are selected by a per-case stable pseudorandom rank across source locations, and remaining clean rows in represented strata can be batch-approved only after every sampled row is approved without correction. Rows in strata that do not fit into the five sample slots stay individual-review exceptions; a correction in the sample disables batch approval for the case. This sample reduces routine review work but is not a statistical guarantee; customer pilots still need format-specific labeled validation.
- Deterministic parser/OCR results are zlib-compressed and cached per case for worker retries using the source-file SHA-256, parser profile, relevant package versions, and OCR configuration. Validated Luna output can also be cached when `RFQ_LLM_DEPLOYMENT_VERSION` explicitly pins an immutable revision; its key also includes model, prompt/schema/validator versions, and exact source segments. Raw derived artifacts are capped at 10 MiB; cache writes require the active lease; changed source/profile and another case cannot hit the artifact; case deletion cascades to cached excerpts. Provider deployment immutability still needs external verification before production use.
- Case processing provenance now includes parser profile hash/cache-hit state, queue-wait and bounded stage timings, Luna model/deployment label, prompt hash, schema and validator versions, extraction/repair/validation call counts, and token usage when supplied by the provider. Queue attempt counts are available in the durable job record; aggregating retry counts into operational metrics remains follow-up work. Empty extraction results skip the second consistency call; no model call is added to deterministic rows. Deployment versioning must be confirmed with the provider.
- External model processing requires customer consent, provider and retention review, and an agreed data region before real RFQs are sent. Synthetic-only use is the current authorized validation scope.
- The model adapter's grounding checks reduce unsupported proposals but cannot prove semantic correctness. They are combined with exact manufacturer+MPN matching, exception routing, and the sample review plan; they are not an accuracy guarantee.
- The second LLM consistency call uses the same configured Luna model and credentials, so it is not an independent model. Treat it only as an extra issue detector; deterministic checks and human review remain the actual gates.
- No representative provider latency, extraction quality, OCR quality, or generalization result has been established. A single-row live Luna smoke confirms request compatibility and the second review pass only; do not treat it as extraction-quality evidence.

## Recommended sequence

1. Replace heuristic candidate-region capture with a formal completeness ledger for every non-empty source row/page; surface any region that has no extracted line or explicit non-line classification.
2. Build broader, held-out human-labeled RFQs per input format and use measured error rates to refine which clean rows qualify for sample-based approval.
3. Upgrade the single-host queue before multi-host production: shared durable state/queue, supervised workers, health signals, documented recovery, and deployment/load testing.
4. Keep a synthetic, versioned benchmark for each format and stage. Report quality separately from latency, memory, and concurrency; include unreadable and adversarial files.
5. Before sending any real RFQ to an external model/OCR service, obtain explicit customer approval and document retention, deletion, region, and human-review responsibilities.

## Verification record for this branch

Offline grounded-extraction tests use fake clients and synthetic snippets to verify schema rejection, numeric/verbatim evidence checks, second-pass conflicts and outages, Luna-only configuration, disabled-by-default behavior, and bounded prompts. A separate live synthetic smoke used only the explicitly authorized GPT-6 Luna Foundry credential from the sentence-validation project. It produced one grounded proposal and passed the second review call; the run used three provider calls total (the initial extraction needed one repair before the review) and took about 5.0 seconds. This is a connectivity/contract smoke on one synthetic row, not an accuracy or latency benchmark.

- Full backend suite on the latest locally validated source: **394 passed**, with 7 dependency deprecation warnings (Starlette/AnyIO, PyMuPDF/SWIG, and `defusedxml`). This includes unfamiliar non-keyword text/PDF retention, candidate-region bounds, Luna fallback recovery, candidate-only XLSX review routing, source-coverage reconciliation, PDF page rendering, sibling-prefix path-traversal rejection, and the rule that unrepresented source strata cannot enter batch approval.
- Legacy `.xls`: seven focused tests passed, including validator rejection, isolated environment, timeout, macro-bearing output rejection, missing-converter failure, parser provenance, and upload-to-match with original retention. A separate local smoke generated a synthetic `.xls` with LibreOffice, converted it back through the ingestion path, and extracted its one expected row. This does not validate arbitrary legacy workbooks or provide OS-level sandboxing.
- Frontend: `npx tsc --noEmit` passed; `npm run lint` passed.
- Synthetic local corpus: **30/30** complete flows (8 CSV, 7 generated XLSX, 8 text, 7 distinct generated native PDFs), including review-plan generation, sample review, batch approval of remaining clean rows, export, and audit. The XLSX inputs span seven layouts with alternate headers, reordered columns, preamble rows, extra columns, and multiple sheets. The PDFs vary across four row formats, portrait/landscape, and page breaks. The runner asserts unique source bytes and full layout representation for both file types, and compares every extracted MPN, manufacturer, quantity, and unit with the generated ground truth: **180/180 critical-field checks passed**.
